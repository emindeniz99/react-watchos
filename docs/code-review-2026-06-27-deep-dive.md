# Deep review — code + design + DX (2026-06-27)

Adversarially-verified multi-agent review (20 reviewers, every finding
independently verified). 64 confirmed of 91 raw — {'blocker': 1, 'major': 11, 'minor': 39, 'nit': 13} by severity, {'code': 27, 'design': 16, 'dx': 21} by category.

## Executive summary

react-native-watchos is an ambitious, largely well-architected custom React renderer for Apple Watch with a genuinely impressive single-source-of-truth codegen pipeline (schema.mjs drives the install table, C trampolines, TS host types, and Swift HostBridge), a thoughtfully-designed OTA + anti-rollback capability gate, and a strong test posture (257 JS / 112 Swift tests passing). The core wire/bridge contract is the project's strongest asset and shows real engineering discipline. However, the review surfaced one true blocker: consumer-path bundles crash at load because `process.env.BUNDLE_VERSION` is read at runtime in update.ts but never injected by the published `buildBundles` helper and there is no `process` shim — so the exact path that ships (anyone importing OTA) fails module evaluation, while the in-repo build masks it. Beyond that, the dominant pattern is a robustness gap between two "second-class" execution contexts and the well-hardened tap path: the widget extension process and the native-push/async-settle paths repeatedly skip the safeguards (generation guards, per-handler isolation, OTA gating, onError wiring, fail-loud) that the main app path implements correctly. Several fallible async operations (BLE write/subscribe, generateText, connect-timeout) can hang JS promises forever or leak state, directly violating the project's own CX-022 "never hangs" and Rule 12 "fail loud" contracts. The OTA story has a credibility problem: the documented production signing flow (ota:sign/ota:keygen) is literally unpublished and unreachable for consumers, and manifest version vs. bundle BUNDLE_VERSION are wired independently with nothing keeping them in lockstep. Finally, documentation has drifted materially from the code (npm vs pnpm, post-prebuild vs in-prebuild, wrong OTA URL, wrong SwiftPM products, stale primitive/test counts) such that a new adopter following the headline README cannot reach a running build. None of these are deep architectural flaws — the design is sound — but the consumer/widget/async edges have not received the same care as the happy path, and the project is not currently shippable to an external consumer until the blocker and the signing/version-wiring gaps are closed.

## Themes

- The consumer path is systematically less verified than the in-repo path. The renderer's own config.mjs masks bugs that only manifest for real consumers: the BUNDLE_VERSION crash (config.mjs injects it, buildBundles doesn't), unpublished ota:sign scripts, manifest-version desync, and a README that documents the demo flow rather than the plugin+scaffold flow. Tests pass because they exercise the in-repo build; the shipped surface is under-tested.
- The widget extension process is a second-class citizen that re-introduces, across process boundaries, the very corruption the main app's gates prevent. It installs watch-only host trampolines as no-op stubs (breaking JS capability detection so generate/fetch hang), never loads the OTA bundle or applies the capability gate, never wires onError (JS exceptions silently swallowed), and runs the JSRuntime off-main while setTimer hardcodes DispatchQueue.main. Multiple findings collapse into one root cause: the shared JSRuntime/HostBridge was designed for the app and reused in the widget without making target-awareness real.
- Fallible async operations violate the project's own 'never hangs / fail loud' contracts (CX-022, Rule 12). BLE write/subscribe and generateText have no timeout and leak both native and JS pending entries; the connect-timeout path doesn't drain queued ops; native-event listeners have no per-handler isolation; runSync skips flush on throw; intent handlers that throw after a write skip publishWidgets. The tap path was deliberately hardened with try/finally — every other async/event path was left strictly weaker for no stated reason.
- The async generation-guard invariant has a hole on the highest-traffic path. Every settle path captures `let gen = generation` and guards except the one that matters most — bridge.commit — letting a stale tree from the old runtime clobber the new one's state and optimistic-ack bookkeeping on reload. The BLE connect-timeout has the analogous invoke-id-collision hole. The invariant the model documents (ARCH-08) is stronger than the code enforces.
- Drift guards are weaker than they appear: the invoke-routing and component-contract tests regex the entire host file for `case "...":`, so they're one-directional supersets that pass falsely if a real case is deleted but the literal appears elsewhere. The SD-1 invoke channel and component PROPS are the two un-generated seams in an otherwise generated bridge, guarded only by these fuzzy regexes — drift relocated, not removed.
- Documentation has drifted from a moving codebase and several docstrings describe automation that doesn't exist (schema.mjs claims minBridgeProtocol/requiredFeatures/since are auto-derived; they're hand-authored). The main README alone has wrong package manager, wrong OTA URL, wrong SwiftPM products, superseded post-prebuild language, stale primitive and test counts — collectively blocking adopter onboarding even though the underlying code works.
- Sensors and synchronous Storage writes are whole fail-silent classes: denied permission or absent hardware gives JS no signal (eternal spinner), and App Group write failures are unobservable. These are the bridges CX-022 left behind, and they're the failure modes hardest to diagnose on a closed-app watch.

## Coverage gaps

- Device/runtime behavior was not executed. All findings are static (code/doc reads, grep, the one shipped example bundle inspection). The BUNDLE_VERSION crash, the BLE/generate hangs, the widget no-op trampoline hangs, the commit-path data race, and the cross-thread QuickJS timer concerns are reasoned from the source but were NOT observed firing on a real watch or simulator — the actual frequency, timing windows, and user-visible severity of the race/hang conditions are inferred, not measured.
- The codegen pipeline output was reviewed as committed generated files, but I did not run `pnpm codegen` to confirm the generators still produce exactly those files from the current schema, nor that a target-aware install fix is mechanically straightforward in generate.mjs.
- Apple-targets coupling (withEasAppExtensions overwrite, base-mod ordering) was verified against one installed version (4.0.7); behavior against other apple-targets versions, and whether a real `expo prebuild` end-to-end produces the claimed broken .pbxproj, was not executed — only reproduced/reasoned in isolation.
- The OTA signature/verification interop (UpdatePlan.signedMessage vs ota-sign.mjs) was read for format agreement but the actual sign→verify round-trip, and whether the unsigned requiredFeatures/minBridgeProtocol tampering is exploitable in practice, was not run.
- Swift host/widget code is #if os(watchOS) and empty off-watchOS, so the Linux `swift test` suite (112 passing, confirmed) exercises only the pure Foundation cores (BleSession, RouteMatcher, RNStyle, UpdatePlan, stores) — none of the Darwin bridge code (BluetoothBridge, SensorBridge, the commit closure, JSRuntime threading) where most of the major findings live. Those paths are unverified by any automated test on any platform.
- I did not independently re-derive whether every one of the 64 findings is non-overlapping; several (e.g. the two near-identical BLE malformed-UUID entries, and the duplicated commit-path race entries) appear to describe the same defect from different angles, so the true distinct-defect count is somewhat lower than 64.
- Performance, memory footprint under sustained use (e.g. the leaked fetch timers / generate pending entries accumulating), and battery impact on-device were not assessed at all — only the existence of the leaks, not their practical magnitude.
- I did not audit areas not represented in the findings set (e.g. the React reconciler integration correctness, the navigation runtime beyond RouteMatcher parity, or accessibility), so absence of findings there reflects review scope, not a clean bill of health.

## Confirmed findings

> **blocker** (process.env.BUNDLE_VERSION) is already fixed (commit 2913e6c).

### [blocker/code] Consumer-path bundles crash at load: process.env.BUNDLE_VERSION is never defined by buildBundles
`js/src/update.ts:84 (+ js/esbuild/preset.mjs:57, examples/expo-watch-app/targets/watch/assets/bundle.js:9999)`

update.ts has a module-level `export const BUNDLE_VERSION = Number(process.env.BUNDLE_VERSION ?? "1")`. The QuickJS preset only `define`s `process.env.NODE_ENV`, and there is NO `process` shim in the runtime (grep of src/shims.ts / install-shims.ts: none; the built example bundle has no `var process`). The renderer's own config.mjs injects `process.env.BUNDLE_VERSION` via define, but `buildBundles` (the published helper every consumer uses) never does. I verified the actual shipped example bundle: line 9999 reads `var BUNDLE_VERSION = Number(process.env.BUNDLE_VERSION ?? "1")` — the bare `process.env.BUNDLE_VERSION` survives un-replaced (while `process.env.REACT_WATCH_OTA_URL`, which the example DID define, was correctly replaced with ""). At runtime in QuickJS `process` is undefined, so this throws a TypeError during module evaluation. update.ts is in the import graph of any watch UI using fetchAndApplyUpdate (the demo and the expo example both import it), so the whole bundle fails to load. The renderer's in-repo `dist` build masks this because config.mjs injects the value; the bug only manifests on the consumer/example path — i.e. exactly the path that ships.

**Fix:** Don't read process.env at runtime for BUNDLE_VERSION. Either (a) have buildBundles inject `process.env.BUNDLE_VERSION` from the per-target `manifest.version` automatically (single source of truth — the manifest version IS the bundle's compat version), or (b) add a minimal `process` shim with an `env` object so an undefined var degrades to the `?? "1"` fallback instead of throwing. (a) is better: it also fixes the disconnect below.

### [major/code] Native-event listeners run with no per-handler isolation; one throw starves the rest
`js/src/nativeEvents.ts:56`

dispatchNativeEvent iterates `for (const handler of [...set]) handler(payload);` with no try/catch around each handler. If any one listener for a native push (e.g. ble.state, watchConnectivity, sensor reading) throws, the loop aborts and every later-registered listener for that same event name is silently skipped for this push. The tap path (renderer.dispatchEvent) was deliberately hardened to survive a throwing handler and still ack/flush (see the finally block at renderer.ts:288-303), so native pushes are strictly less robust than taps for no stated reason. Concrete consequence: an unrelated screen's listener that throws once can stop a connection-state or incoming-message listener from ever seeing that event, and the data the push carried is dropped.

**Fix:** Wrap each handler call in try/catch and route the error to the runtime's fail-loud channel (console.error / onError) so a throwing listener is surfaced but does not prevent the other registered handlers from receiving the payload. Match the isolation the tap path already guarantees.

### [major/code] bleWrite/bleSubscribe issued without an active connection hang the JS promise forever (no timeout)
`js/src/bluetooth.ts:77-97 (root cause js/swift/Sources/ReactWatchHost/BluetoothBridge.swift:196-236)`

Only bleConnect arms a timeout (BluetoothBridge.swift:83 armConnectTimeout; connect rejects with UNAVAILABLE after 15s). bleWrite and bleSubscribe have no timeout. When they are called while peripheral == nil and no connect is in flight (e.g. consumer calls bleWrite/bleSubscribe before bleConnect, or after a connect already failed/timed out), write() queues the invoke id in session.pendingWrites (BluetoothBridge.swift:201-207) and subscribe() records it in pendingSubscribes (line 228-236) — both keyed to a live JS invoke id. Those native entries are only drained by didDisconnect, finishDiscovery, or bleDisconnect (takeAllPending). If no connection ever materializes, none of those fire, so the native pending entry AND the JS Promise in invoke.ts's `pending` map both sit forever. invoke.ts has no client-side timeout, so the awaiting JS code (e.g. `await bleWrite(...)` in a useEffect or button handler) hangs. The bluetooth.ts header promises 'Never hangs' / settled promises (CX-022), but this path violates that for the most common API misuse.

**Fix:** Arm a per-op timeout (or a 'no connection / not connecting' fast-reject) for bleWrite/bleSubscribe the same way bleConnect does, rejecting with UNAVAILABLE. Cheapest: in BluetoothBridge.write()/subscribe(), when peripheral == nil AND session.shouldAutoReconnect is false / no connect is pending, reject the invoke immediately instead of queueing; otherwise arm a timeout mirroring armConnectTimeout so a queued op that never flushes still settles.

### [major/code] Generated install table ignores `targets`: widget runtime installs watch-only host functions as live no-op trampolines, breaking JS capability detection
`js/codegen/generate.mjs:159-162 (hostBridgeSwift install loop) → js/swift/Sources/ReactWatchRuntime/Generated/HostBridge.swift:35-87; consumed by js/swift/Sources/ReactWatchWidget/WidgetIntentRuntime.swift:38-52`

`installHostBridge` is generated from `directMethods` with NO per-target filtering, and is called unconditionally from the shared `JSRuntime.init` (JSRuntime.swift:395). So the widget's `WidgetIntentRuntime` (which reuses the same JSRuntime) installs ALL 17 direct host functions onto `__host`, including the 7 watch-only ones — playHaptic, cancelNotification, fetch, abortFetch, ble, sensor, generate. WidgetIntentRuntime only assigns closures for commit/publishWidgets/getItem/setItem/counterGet/counterAdd, so the watch-only trampolines run with a nil `bridge.X?` closure and silently no-op. This corrupts the JS-side capability checks that the framework relies on: src/ai.ts:69 does `if (!host?.generate) reject('on-device AI unavailable')` — in the widget `host.generate` is a truthy installed function, so the guard passes, a pending callback is registered (ai.ts:74), `host.generate(id, …)` no-ops, and the returned Promise NEVER settles (hang). src/fetch.ts:294 (`__host?.fetch?.(…)`) and the BLE channel have the same shape. The schema docstring (schema.mjs:192-194) explicitly claims `targets` controls 'which native runtime installs each method' and that 'the cross-check test asserts each side installs exactly its listed methods' — but no such per-target install test exists (codegen.test.ts:21-42 checks the install table is target-AGNOSTIC), and release-contract.test.ts:33-38 asserts the widget binary 'genuinely lacks' network/ai at the feature-set level while the runtime actually exposes those functions. The demo widget.entry.tsx happens not to call generateText/fetch, so it's latent today, but index.ts re-exports them to every consumer and a widget intent handler calling either would hang.

**Fix:** Make `installHostBridge` honor `targets`: either generate two install methods (e.g. `installHostBridge(into:context:)` for watch and a widget variant that installs only `directMethods.filter(m => m.targets.includes('widget'))`), or pass a target enum and branch the JS_SetPropertyStr calls. Then add the per-target install cross-check test the schema docstring already promises (assert the watch install set == direct methods targeting watch, widget install set == direct methods targeting widget). Until the install table is target-aware, the schema docstring's claim is false and should not be left as-is.

### [major/code] BLE connect timeout rejects only the connect promise, leaking any write/subscribe queued before the connection
`js/swift/Sources/ReactWatchHost/BluetoothBridge.swift:113-126`

bleWrite/bleSubscribe are independent invokes that JS can call before bleConnect resolves (the JS API in bluetooth.ts does not gate them). When not yet connected, write() queues the write with its invokeId (line 202-206) and subscribe()/awaitSubscribe records a pending subscribe id. If the connection never succeeds, armConnectTimeout fires and does only `central?.stopScan()` + reject(connect_id) — it never calls session.takeAllPending(). So the queued write/subscribe invoke ids are never settled and `stopScan()` means nothing will ever flush them: those JS promises hang forever. This is precisely the hung-promise failure mode CX-022 set out to eliminate (disconnect() at line 168-174 correctly drains takeAllPending(); the timeout path does not).

**Fix:** In the connect-timeout handler, after determining the connect actually timed out, also drain and reject the rest of the in-flight set (session.takeAllPending()) with "UNAVAILABLE"/"connect timed out", mirroring disconnect(). didFailToConnect keeps scanning so its queued writes can still flush, but the timeout path stops scanning and must not leave them pending.

### [major/code] commit→decode→main settle path is the one async settle that is NOT generation-guarded (CX-008 gap)
`js/swift/Sources/ReactWatchHost/ReactWatchHost.swift:858-901`

Every other async settle path captures `let gen = generation` and checks `gen == self.generation` before touching the runtime/model (fetch L1017/1021, generate L646/659, notification L975/978, sendToPhone L318/321, requestNotificationPermission L289/294). The `js.bridge.commit` closure is the exception: it hops `decodeQueue.async` (background serial queue) → `DispatchQueue.main.async` capturing only `[weak self]`, with NO generation capture or check. The decode-to-main hop is asynchronous, and `boot()` (which runs on the @MainActor model — e.g. dev hot-reload from `pollDevServer`, or native OTA `checkForUpdateNatively`/recovery) bumps `generation`, sets `runtime = nil`, and resets `root=nil`/`ackedSeq=0`/`nextSeq=1`/`optimistic=OptimisticStore()`. A tree committed by the OLD runtime, still in flight on `decodeQueue` when `boot()` runs, lands its main continuation AFTER the reset and writes `self.root = tree.root` (a previous-generation SwiftUI tree), advances `self.ackedSeq`/`self.optimistic.ack(throughSeq:)` against the fresh seq space (which restarted at 1), and can flip the crash-loop counter via `promoteToKnownGood`. This directly contradicts the model's own stated invariant (ARCH-08 doc: "the generation guard → no old async settles a new runtime"; the CX-008 comment at L62-66). Consequence: a stale tree briefly renders over the freshly-booted bundle and corrupts optimistic-ack bookkeeping for the new generation. It is not a memory-safety bug (no JS context is touched — `self.root` is pure SwiftUI state), but it is a real cross-reload data race in the model state the guard exists to protect.

**Fix:** Capture `let gen = generation` at the top of the `commit` closure (before the `decodeQueue.async`) and add `guard gen == self.generation else { return }` inside the `DispatchQueue.main.async` block, exactly as the other settle paths do. The wire-version check and all subsequent `self.root`/`ackedSeq`/`optimistic` mutations should sit behind that guard.

### [major/design] In-prebuild native wiring swallows every error, deferring a build-critical failure to a confusing Xcode error
`js/plugin/withNativeWiring.js:69-90`

The base-mod action wraps wireLocalPackage + mergeTargetInfoPlists in a try/catch that downgrades ANY failure to console.warn(`native wiring skipped: ${error}`) and returns the config unchanged. Linking the SwiftPM host products is build-critical: if it is skipped, the .pbxproj has no XCSwiftPackageProductDependency for ReactWatchHost, and the watch app fails to compile with `no such module 'ReactWatchHost'` — a message that points at the Swift source, not at the prebuild step that silently no-op'd. The warning is buried in verbose `expo prebuild` output and easily missed. This directly contradicts the repo's own Rule 12 ("Fail loud" / "'Completed' is wrong if anything was skipped silently"). A genuine wiring failure (e.g. a node-xcode parse error or a renamed apple-targets internal) is exactly the case that should abort prebuild, not be hidden.

**Fix:** Narrow the catch: let a real failure throw (or rethrow with a clear `[react-native-watchos] failed to link SwiftPM products — run \`node node_modules/react-native-watchos/plugin/link-swift-package.cjs\`` message). The only condition that should be tolerated quietly is the already-handled "target not generated yet" (wireLocalPackage already skips unknown targets internally and returns linked:[]), so the broad catch is guarding against the wrong thing.

### [major/design] Widget process never loads the OTA bundle — OTA + the entire version/capability gate are bypassed in the extension
`js/swift/Sources/ReactWatchWidget/WidgetIntentRuntime.swift:65-84`

WidgetIntentRuntime.loadBundle() loads ONLY the shipped Bundle.main bundle.qbc/bundle.js. It never reads the persisted OTARecord (ota-bundle.json), never calls VersionPolicy.decide / CapabilityGate, and has no anti-rollback or crash-loop logic. Yet this same runtime executes intent handlers (__handleIntent) and renders timelines (__renderWidgets), and it mutates the SHARED App Group: SharedWidgetStore Storage (getItem/setItem) and CoordinatedCounterStore counters, then republishes timelines. The design this implements (docs/design-ota-capability-gate-2026-06-25-1847.md, SD-4/CX-004, lines 129-131) explicitly requires: 'Widget participates: IntentRuntime reads the same active record and applies the same gate at boot.' The implementation does neither. Consequence: after ANY OTA update, the app process runs the new bundle (possibly a breaking wire/schema/contract bump that drove a bundleVersion increment) while the widget process stays pinned to the shipped v1 bundle and keeps writing the same shared Storage/counters with stale logic. This re-introduces, ACROSS PROCESSES, the exact 'old code against newer-schema data' corruption the whole anti-rollback gate exists to prevent — and it does so silently, with no gate, no version check, and no test (no widget-OTA test exists). An OTA can never actually fix a widget-side bug, and a breaking OTA actively desyncs the two processes against shared state.

**Fix:** Make the widget runtime go through the same OTA path: read the active OTARecord (or a widget-specific OTA record built from ARCH-03's widget.bundle.js target), apply VersionPolicy.decide + CapabilityGate against HostFeatures.widget at boot, and fall back to shipped only when blocked — exactly as ReactWatchHost.load does. At minimum, factor the record-load + gate decision into a shared type in ReactWatchSupport that both ReactWatchHost and WidgetIntentRuntime call, and add a widget-gate test (blocked/downgraded bundle ⇒ widget runs shipped and makes no App-Group writes), matching the SD-4 test plan item 'Widget gate: blocked bundle ⇒ no App-Group writes.'

### [major/design] BLE connect-timeout closure isn't generation-scoped — a stale timeout can stopScan + reject a NEW runtime's bleConnect that reused the same invoke id
`js/swift/Sources/ReactWatchHost/BluetoothBridge.swift:113-126`

`armConnectTimeout(id:)` schedules a 15s main-queue timer capturing the persistent BluetoothBridge and the raw invoke `id`. Invoke ids are JS-module-scope (`nextInvokeId` in js/src/invoke.ts:32) and reset to 1 with every new QuickJS context, so ids COLLIDE across generations. On reload, `boot()` calls `bluetooth.resetPendingForReload()` (ReactWatchHost.swift:160) which clears `pendingConnect`, but the already-scheduled timeout from the old generation is NOT cancelled. Scenario: old runtime issues bleConnect (id=1), reload happens before it connects, new runtime issues a fresh bleConnect (also id=1, sets pendingConnect=1). When the OLD timer fires it checks `bridge.session.pendingConnect == id` (1==1, true), calls `central?.stopScan()` and rejects pendingConnect=1 — which is now the NEW runtime's live connect promise. The new runtime's bleConnect rejects spuriously with 'connect timed out' and scanning is aborted under it. The id-collision-after-reload risk is precisely the hazard the host comments call out for the invoke map (ReactWatchHost.swift:150-153), but the BLE connect timeout has no equivalent guard.

**Fix:** Give the timeout an epoch: capture a per-connect token (or the host `generation`) and verify it before acting, OR have `resetPendingForReload()` invalidate outstanding connect timeouts (e.g. bump a `connectEpoch` the closure compares against). The pure check belongs in BleSession so it stays Linux-tested.

### [major/design] Manifest version and the running bundle's BUNDLE_VERSION are wired independently — silent anti-rollback drift
`examples/expo-watch-app/scripts/build-targets.mjs:29-32 + js/src/update.ts:84`

In the consumer flow the manifest's `version` is set in the build script (`manifest: { version: 1 }`), but the running bundle's `BUNDLE_VERSION` (what isFresherRelease compares against, update.ts:176-177) comes from a SEPARATE channel: `process.env.BUNDLE_VERSION`, which buildBundles never injects. So even once the load crash above is fixed, a consumer who bumps `manifest.version` to 2 for a breaking release has no wired way to make the shipped bundle report version 2 — it stays at the hardcoded fallback `1`. The two numbers that the entire anti-rollback / freshness gate depends on (CR-17, CX-025) are set in two unrelated places with nothing keeping them in lockstep. This is a footgun precisely where correctness matters most.

**Fix:** Make `manifest.version` the single source: have buildBundles inject `process.env.BUNDLE_VERSION` = the target's `manifest.version` into that target's define automatically, so the bundle and its manifest can never disagree. Document that bumping the version is a one-place edit.

### [major/dx] ota:sign / ota:keygen are not published — the documented production signing flow is unreachable for consumers
`js/package.json (files array) + js/scripts/ota-sign.mjs, js/scripts/ota-keygen.mjs`

docs/ota-signing.md, the published esbuild/manifest.mjs header (3x: 'sign with ota:sign', 'fill it at publish time with ota:sign'), and the expo example README ('Sign manifests for production with the renderer's ota:sign') all tell a consumer to run `ota:sign` / `ota:keygen`. But `files` in js/package.json is [src, esbuild, app.plugin.js, plugin, swift/..., bin] — `scripts/` is NOT included, and the `ota:keygen`/`ota:sign` npm scripts live only in the renderer's own package.json, not a consumer's. So a consumer who `npm install react-native-watchos` gets neither the scripts nor the .mjs files. Worse, ota-sign.mjs imports `./config.mjs` and hardcodes `dist/bundle.js` + `bundleVersion` — repo-internal assumptions that don't fit a consumer who builds via buildBundles to `targets/watch/assets/`. The entire signing story (the thing that turns OTA from in-sandbox RCE into something safe, per CR-4) is reachable only from inside this repo. Without it, signerPublicKeys stays empty and the app is fail-open by the docs' own admission (ota-signing.md:31). Net: production OTA cannot be signed by a real consumer.

**Fix:** Ship signing as a published entry point: add a `signManifest({ distDir, bundleFileName, version, key, keyId })` helper to esbuild/manifest.mjs (already published as react-native-watchos/manifest) that takes the bundle path + key explicitly, and/or expose `ota:keygen`/`ota:sign` via the published `bin`. Then point all docs at that. ota-sign.mjs's hardcoded dist/ + config.mjs import must not be the consumer surface.

### [major/dx] README's main OTA instructions set REACT_WATCH_OTA_URL to a bundle URL, but it must be the manifest endpoint
`README.md:244 and README.md:249`

The renderer README tells you to build with `REACT_WATCH_OTA_URL=http://127.0.0.1:8788/bundle.js`. But that env var is consumed by demo/App.tsx:400 as `fetchAndApplyUpdate(OTA_UPDATE_URL)`, which does `fetch(manifestUrl)` then `.json()` (update.ts:204/230). Pointing it at `/bundle.js` fetches the JS bundle and tries to JSON.parse it → guaranteed failure. The demo's own code comment (App.tsx:384) correctly calls it 'the manifest endpoint', and the expo example README correctly uses the base URL `http://127.0.0.1:8788` (manifest resolved as /manifest.json). The renderer README contradicts both. A user following the headline README OTA recipe gets a parse error, not an update. The same README section also never mentions building/serving manifest.json at all — it only talks about serving dist/bundle.js, so even the URL aside, the documented flow has no manifest to fetch.

**Fix:** Change README.md:244/249 to point REACT_WATCH_OTA_URL at the manifest base (e.g. http://127.0.0.1:8788, served from dist/ which `build` now stamps manifest.json into), matching the expo example. Mention that `build` writes dist/manifest.json and the dev server serves it.

### [minor/code] <Text> leaks `false`/`true` boolean children as the literal strings "false"/"true"
`js/src/serialize.ts:8`

`textContent` folds Text children with `return String(children)` for any non-array, non-null value. React/React-Native render boolean, null, and undefined children as nothing, but `String(false)` is "false" and `String(true)` is "true". The most common React idiom inside Text — `<Text>Label{show && " *"}</Text>` — therefore renders "Labelfalse" on the watch when `show` is false. Verified by direct probe: `<Text>{"Label"}{show && " *"}</Text>` with show=false serializes props.text === "Labelfalse"; an array containing `true` yields "...true...". The TextProps.children type (`string | number | Array<string|number>`) excludes booleans at the type level, but `cond && "x"` widens to `false | "x"` and routinely slips through composition/casts, so this is a live, user-facing bug, not just a type-discipline issue.

**Fix:** In `textContent`, skip values React treats as empty before stringifying: e.g. `if (children == null || typeof children === "boolean") return "";` (and keep the array branch recursing so per-element booleans/nulls are dropped too). Add a render test asserting `<Text>a{false}{null}b</Text>` folds to "ab".

### [minor/code] runSync skips flush when a native-event listener throws, losing already-applied state
`js/src/renderer.ts:314`

__pushNativeEvent (index.ts:224) routes native pushes through root.runSync(() => dispatchNativeEvent(...)). runSync runs `fn()` inside a try/finally that only restores currentUpdatePriority; `this.flush()` is the statement AFTER the try/finally (line 323), so if `fn()` throws (a native-event listener throwing — see the companion nativeEvents.ts finding) the exception propagates and flush() is never reached. Any React state that listeners which ran BEFORE the throw already enqueued is left unflushed/uncommitted until the scheduler's next default-priority turn — exactly the 'commit instantly like a tap' guarantee this path exists to provide. The tap path solves this by flushing inside a finally (renderer.dispatchEvent, lines 290-302); runSync does not.

### [minor/code] generateText can hang forever — no timeout, no abort, pending entry leaks

### [minor/code] fetch timeout sugar arms a host timer that is never cleared on normal completion

### [minor/code] utf8ToBytes mis-encodes lone/unpaired surrogates instead of U+FFFD
`js/src/fetch.ts:167-189`

The hand-rolled UTF-8 encoder only pairs a high surrogate (0xD800-0xDBFF) when a next char exists (line 175). A trailing lone high surrogate, a high surrogate followed by a non-low-surrogate, or a lone low surrogate (0xDC00-0xDFFF) all fall through to the final 3-byte `else` branch (line 184-186), which emits the raw surrogate code point as a 3-byte sequence — invalid UTF-8 (encodes a value in the U+D800-U+DFFF range). A standards TextEncoder substitutes U+FFFD. **Fix:** In the surrogate branch, verify the next code unit is actually a low surrogate (0xDC00-0xDFFF); if the high surrogate is unpaired, or the char is a lone low surrogate, push the U+FFFD sequence (0xEF,0xBF,0xBD) instead of falling into the 3-byte path.

`js/swift/Sources/ReactWatchHost/ReactWatchHost.swift:858-901`

`assertMainThread` and its doc comment state the contract as absolute: "every method that touches the JS context ... MUST run on the main thread (OP-2)" and "All current callers were audited on-main." But that audit only covers the watch-host callers. The widget extension drives the SAME `JSRuntime` class through `evaluate` (L78), `evaluateBool` (L210), `evaluateString` (L225), `callReturningBool`/`callReturningString` (L340/352) and `drainJobs` (L418) — none of which call `assertMainThread()` — from WidgetKit provider callbacks (`getTimeline`/`getSnapshot` completion handlers, ReactTimeline.swift:185-199) and `AppIntent.perform()` (ReactWidgetButtonIntent.swift:25, `async`), which are NOT guaranteed to be the main thread. This happens to be safe because each `WidgetIntentRuntime` constructs its own private `JSRuntime` and never shares it across threads (single-thread-confined per instance), so the real invariant is "each context is confined to one thread," not "the main thread." The stated model is therefore stronger than the code enforces, and `setTimer` (JSRuntime.swift:400-409) unconditionally schedules on `DispatchQueue.main` — so any timer the widget bundle sets during eval is posted to a main queue the short-lived off-main extension call won't pump, silently orphaning it. Not a live crash today, but the invariant as documented is misleading and the timer-on-main assumption is false for the widget runtime.

**Fix:** Tighten the doc/model to the actual invariant: a JSRuntime instance is confined to a single thread for its lifetime (main for the host, the provider's thread for the widget). Either (a) make `setTimer` schedule onto the runtime's owning queue rather than hard-coding `DispatchQueue.main`, or (b) document that the widget intent/render path is synchronous and must not rely on timers, and assert thread-confinement (same-thread, not main-thread) in debug. At minimum, correct the `assertMainThread` comment so it doesn't claim a universal main-thread rule the widget path knowingly violates.

### [nit/design] requiredFeatures / minBridgeProtocol are not covered by the OTA signature
`js/swift/Sources/ReactWatchSupport/UpdatePlan.swift:108-111`

signedMessage() covers only "<scheme>:<keyId>:<version>:<js>"; ota-sign.mjs (scripts/ota-sign.mjs:62-66) signs the identical string. The capability fields requiredFeatures and minBridgeProtocol travel in the manifest/payload unsigned and are consumed by the CapabilityGate at saveUpdate (ReactWatchHost.swift:391-401). A man-in-the-middle who tampers the manifest can strip a bundle's requiredFeatures so the capability gate passes a bundle that actually needs a missing host method; the bundle then applies and only fails later at the JS runtime guard (CapabilityError) rather than being cleanly blocked with 'update the app'. This is not RCE (the js bytes are still signature-protected, so an attacker can't substitute a malicious bundle), so it's a UX/robustness weakening of the gate rather than a security break — but the design framing (signedMessage doc, lines 12-18: 'the key id and version are inside the signed data ... can't be relabelled') implies the gate inputs are protected, and these two are not.

**Fix:** Either fold the capability fields into the signed bytes (e.g. "v1:<keyId>:<version>:<minBridgeProtocol>:<sortedFeatures>:<js>" — update UpdatePlan.signedMessage, ota-sign.mjs, and OTASigningInteropTests together, per the pre-release 'change the format in place' rule), or document explicitly that these fields are intentionally unsigned because tampering can only make the gate stricter or trip the runtime guard, never bypass js-signature verification.

### [nit/design] Widget runtime's QuickJS timers/microtasks can be scheduled but never fire — the extension process dies after the synchronous eval
`js/swift/Sources/ReactWatchWidget/WidgetIntentRuntime.swift:91-124`

WidgetIntentRuntime drives JS purely synchronously: `__handleIntent`/`__renderWidgets` are called via callReturningBool/String, which `drainJobs()` (microtasks) but do NOT run the main run loop. If a registered intent handler or widget render schedules a timer (`setTimeout`) or awaits a real async op (fetch/invoke — neither is wired in the widget runtime's bridge, getHost().invoke is undefined there so invoke() rejects immediately, OK), the scheduled DispatchWorkItem (`scheduleTimer`, JSRuntime.swift:400) is enqueued on `DispatchQueue.main` but the extension returns from the synchronous call and the WidgetIntentRuntime (and its JSRuntime) is deallocated before the timer deadline — the JSRuntime deinit cancels pendingTimers, so the timer's JS callback silently never runs. A handler that does `setTimeout(() => publishWidgets(...))` (a plausible JS pattern) will appear to do nothing in the widget, with no error. This is a real semantic gap between the app runtime (run-loop-alive) and the widget runtime (synchronous-only) that isn't surfaced to JS.

**Fix:** Either document loudly (in WidgetIntentRuntime and js/src/widgets.ts) that intent/render handlers must be synchronous — no timers/await — or detect a non-empty pendingTimers/unsettled-promise state after the synchronous call and onError it so the gap fails loud instead of vanishing.
